Os loaders das páginas de evento, provedor e jogo também devem deixar de validar recursos apenas contra os snapshots.

## 5. Configuração: campo por campo e destino

Os campos abaixo também produzem comportamento visível e precisam entrar no planejamento. Famílias como display_* e social_* foram mantidas como famílias porque o próprio guia não enumera todas as chaves. Destinos marcados “a confirmar” são inferências de encaixe, não contratos afirmados pelo documento. Quando o guia apenas enumera uma chave, tipos, unidades, valores possíveis e precedência ainda precisam do contrato completo; o encaixe na UI não resolve essas lacunas.

## 7. Contratos transversais que precisam ser respeitados

### Tenant, BFF e sessão

Fluxo proposto para a integração, ainda não implementado:

`Navegador → /api/backoffice/{path} → resolver tenant do Host → cookie HttpOnly/JWT → https://{base_url}{path}`

No SSR, o servidor reutiliza o mesmo resolvedor e chama diretamente o painel. Redis/CDN/modelos de sessão ficam numa camada de servidor compartilhada. Arquivos como src/server/tenant.ts, backoffice-client.ts e adaptadores por domínio seriam propostas de organização, não arquivos existentes.

O proxy precisa de destinos e operações permitidos, escolhidos a partir do tenant confiável; path/query/body do cliente não podem selecionar outro host. A identidade do tenant deve participar do isolamento de sessão/dados. O cookie local atual já é HttpOnly, mas sua existência não cria autenticação JWT no painel.

Enviar Accept: application/json, Accept-Language: pt-BR, X-Timezone, Client-version, Content-Type quando houver JSON e Authorization nas rotas protegidas. O valor/formato de Client-version não está especificado. Timezone é preferência de apresentação/envio, não autorização para uma aposta.

Somente online/cambista são níveis admitidos pelo guia. Escolher endpoints antes de chamar; nunca testar rotas /api/online/* com uma sessão cambista. 401 limpa a sessão. Tratar 403/422 como erro de negócio conforme resposta, com a exceção explícita do fallback de autenticação online.

A lista de tenants tem cache de 60 s por processo/último valor válido. As respostas do painel não devem ser cacheadas pelo frontend. O JSON de parâmetros CDN também deve ser buscado sem cache conforme o guia. Não confundir essas políticas com cache de imagens públicas.

A normalização deve ser seguida pela busca front_url. O fallback {site_id}.oficial2.com e painel-{site_id}.oficial2.com é uma regra específica descrita; domínio desconhecido mostra Site não encontrado. Parâmetros CDN ausentes mostram Site indisponível. O not-found atual só trata caminho/recurso desconhecido.

### Odds, limites, registro e apresentação

- Conservar IDs reais de esporte/liga/evento/mercado/opção e adaptar snake_case para o modelo de UI. Não usar nome traduzido como identidade.
- Na grade, league abre um grupo e event pertence a esse grupo. cotation é o preço; no destaque curado os campos descritos são id/market/option/price/enabled/boost.
- O turbo já vem no preço. Simples/múltiplas usam o preço recebido; Criar Aposta usa original_cotation; no ao vivo o turbo não vale. Não aplicar novamente o percentual.
- Mercado de pagamento antecipado é identificado por internal=vencedor-do-encontro-pa. Ter o selo visual não significa que qualquer odd foi liquidada antecipadamente.
- Tratar up_price/correct_price como mudança de preço que exige estado de revisão/aceitação conforme contrato; não mostrar apenas erro genérico nem aceitar silenciosamente.
- Backend define limites, compatibilidade e aceitação. Não manter constante local de 30 palpites/13 pernas/valores/prêmio como regra universal sem confirmação.
- Tradicional usa pule_errors por item. Combinadas duque/terno enviam valor cru 10x11x12, várias unidas por hífen; backend conta combinações. Loterias misturadas omitem lottery.
- Manter as grafias change-pasword, cancela-bilhete e seller-tradicional. Não corrigir URLs do painel.
- O documento não detalha idempotência/chaves de operação. operationId do demo é uma garantia apenas local; não assumir que o painel o aceita ou repetir registros financeiros após timeout.

### Pagamentos e estados visuais já ajustados

Depósito: gerar cobrança real → exibir QR/código → consultar /api/check-payment → atualizar saldo → mostrar WalletResult com animação. Saque: ler dados/config → consultar can-withdraw → solicitar → exibir estado retornado/histórico. A palavra confirmado em um resultado deve corresponder a um estado real, não ao clique do usuário.

PIX de pré-bilhete é outro fluxo e usa /api/status-payment. Este endpoint não confirma depósitos de carteira. O guia também não descreve cancelamento de cobrança, estorno, comprovante de saque ou reconciliação pelo frontend; não criar botões operacionais com contratos presumidos.

Ao registrar uma aposta, manter a experiência já corrigida: toast Bilhete registrado. e atualização de saldo/histórico. Não há necessidade de reintroduzir modal Aposta feita para usar o comprovante do backend.

7. Depósito: identificador exigido no polling, intervalo, expiração e retomada de cobrança pendente. Saque: chave Pix, edição, rollover, estados e código promocional.

11. Operações ausentes para contato/endereço/preferências/aparelhos/limites pessoais/recompensas, se essas telas forem conectadas ao backend real.
12. Significado dos campos CDN não detalhados, precedência dos limites/configurações, ações dos banners e o que fazer com tenant disabled.
